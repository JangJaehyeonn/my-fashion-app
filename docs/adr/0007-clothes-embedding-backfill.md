# 0007. 기존 옷 임베딩·속성 백필 방식 (기동 시 백그라운드 ApplicationRunner)

- 상태: 채택
- 날짜: 2026-11-22
- 관련: FR-08, #24

## 배경
FR-07 이전에 등록한 옷은 `clothes.embedding`과 새 속성(fit·material·pattern·season)이 비어 있다. FR-08은 기동 시 임베딩이 빈 옷을
배치로 채우되 실패해도 기동은 계속하고, 사진을 다시 분류해 새 속성까지 채우는 작업은 `wearon.backfill.reclassify=true`일 때만
도는 ApplicationRunner(기본 false)로 만들라고 한다. 제약은 다음과 같다.
- AI 서버가 느리거나 다운이어도 기동(HTTP 응답 시작)이 늦어지거나 실패하면 안 된다.
- 분류는 옷마다 유료 비전 호출이라 기본으로 돌면 안 된다. 임베딩은 `/ai/embed`의 `texts` 배치(최대 100개)로 한 번에 보낼 수 있다.
- 새 의존성·스케줄러·테이블을 늘리지 않는다.

## 결정
- `ClothesEmbeddingBackfill`(ApplicationRunner, 늘 켜짐)이 기동 때 데몬 스레드 하나에서 임베딩이 빈 분류된 옷을 id 순 keyset 페이지(50벌)로
  읽어 페이지마다 `/ai/embed {"texts"}` 한 번으로 채운다. 저장할 수 있는 것이 하나도 없는 페이지(AI 다운·잘못된 응답)가 나오면 그 실행은
  멈추고, 다음 기동 때 다시 시도한다. 미분류 옷은 임베딩 텍스트가 없으므로 대상이 아니다.
- `ClothesReclassifyBackfill`(ApplicationRunner)은 `@ConditionalOnProperty(wearon.backfill.reclassify=true)`라 기본 설정에서는 빈 자체가
  없다(분류 API 호출 0회). 켜면 새 속성 네 개가 모두 빈 옷의 사진을 다시 분류해 **비어 있는 칸만** 채우고(미분류 옷은 분류 결과 전체),
  임베딩을 다시 계산한다. 분류가 연속 3번 실패하면 멈춘다.
- 실행 순서는 `@Order`로 `ClothesEmbeddingStore`(pgvector 준비) → 재분류 백필 → 임베딩 백필. 두 백필 모두 `run()`은 작업을 스레드에 넘기고
  바로 끝나며, 스레드 안의 예외는 로그만 남긴다.

## 검토한 대안
| 대안 | 장점 | 단점 | 버린 이유 |
| --- | --- | --- | --- |
| `run()` 안에서 동기로 백필 | 단순, 끝난 시점이 명확 | AI가 느리면(타임아웃 30초 × 페이지) 기동이 그만큼 늦어짐 | "실패해도 기동은 계속" 취지와 어긋남 |
| `@Scheduled` 주기 작업 | 기동 후에도 계속 채움 | 스케줄링 활성화·주기 설정이 새로 필요, 요구사항 범위 밖 | 요구사항은 기동 시 1회 |
| 재분류가 분류 결과로 전부 덮어쓰기 | 구현 단순 | 사용자가 고친 카테고리·색·이름이 사라짐 | 사용자 수정 값을 지키는 쪽을 택함 |
| 옷마다 `/ai/embed {"text"}` 호출 | 기존 메서드 재사용 | 옷 수만큼 왕복 | "배치로 채운다" 요구, 배치 API가 이미 있음 |

## 결과
- 기동은 AI 상태와 무관하다. 임베딩이 다운이면 빈 채로 남고 다음 기동 때 채워진다.
- 백필은 인스턴스가 여러 대면 각자 돈다. 같은 값을 다시 쓸 뿐이라 결과는 같지만 AI 호출이 중복된다. 인스턴스가 늘면 분산 락을 다시 본다.
- 재분류는 새 속성이 하나라도 채워진 옷은 건너뛴다. AI가 네 속성을 모두 모른다고(null) 답한 옷은 다음에 켜고 기동할 때 다시 분류된다.
