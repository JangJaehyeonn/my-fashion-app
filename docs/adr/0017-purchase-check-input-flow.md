# 0017. 살까 말까 입력 흐름: 고를 때 압축하고 한 화면 상태 머신으로 진행

- 상태: 채택
- 날짜: 2026-11-23
- 관련: FR-17, #54

## 배경
살까 말까는 촬영·갤러리·상품 주소 세 경로에서 사진 한 장을 받아 같은 확인 단계로 이어져야 한다.
업로드 이미지가 압축되는지를 ViewModel·Repository 단위 테스트로 확인해야 하는데, 기존 `ImageCompressor`는
`android.graphics`를 써서 JVM 단위 테스트에서 돌지 않고, `ProductPageRepository`는 실제 네트워크를 쓰는 구체 클래스라 가짜로 바꿀 수 없었다.
분석 중 화면은 단계를 시간으로 넘기되 응답이 오면 바로 결과로 가야 한다.

## 결정
- 압축은 사진을 고른 직후 한 번만 한다. `PurchaseCheckRepository.compress`가 `UploadImageCompressor`(기본 구현은 `ImageCompressor`)로
  JPEG를 만들고, `check`는 압축된 `CompressedPhoto`만 받아 `image/jpeg`로 올린다. 압축에 실패하면 원본을 올리지 않고 다시 고르게 한다.
- `UploadImageCompressor`와 `ProductImageSource`(상품 페이지 조회·이미지 내려받기)를 인터페이스로 두고 `di/ImageModule`에서 바인딩한다.
- 세 경로·확인·분석 중·결과를 `purchase_check/{source}` 한 화면의 단계(`PurchaseStage`)로 진행한다. 단계 표시는 타이머 코루틴이,
  결과 전환은 요청 코루틴이 맡고, 응답이 오면 타이머를 취소한다.

## 검토한 대안
| 대안 | 장점 | 단점 | 버린 이유 |
| --- | --- | --- | --- |
| 업로드 직전에 압축 | 확인 단계가 원본 미리보기 | 재시도마다 다시 압축, 실패를 늦게 앎 | 압축 실패를 사진 고를 때 알려주는 편이 낫다 |
| 압축 실패 시 원본 업로드(옷장 등록 방식) | 구형 기기 HEIC도 진행 | 수 MB 업로드, 형식 거절 가능 | 요구사항이 압축을 기준으로 삼는다 |
| 경로·단계마다 별도 화면과 ViewModel | 화면이 작다 | 사진·가격을 화면 사이로 넘겨야 함 | 바이트 배열을 내비게이션 인자로 넘기기 어렵다 |
| Robolectric으로 실제 압축 테스트 | 실제 비트맵 검증 | 새 테스트 의존성 | 인터페이스 가짜로 충분하다 |

## 결과
세 경로가 같은 `CONFIRM` 단계와 같은 압축 사진으로 모인다는 점을 JVM 단위 테스트로 확인할 수 있다.
결과 단계는 FR-18이 전체 결과 화면으로 바꿀 때까지 +N과 코디 수 등 핵심 값만 보여준다.
구형 기기에서 디코딩할 수 없는 사진은 쓸 수 없으므로, 그런 신고가 생기면 원본 업로드 대안을 다시 본다.
