# 0008. 코디 수 엔진의 규칙 파일 형식과 기본값

- 상태: 채택
- 날짜: 2026-11-22
- 관련: FR-09, #25

## 배경
대표 숫자 +N 코디는 LLM 없이 결정적인 규칙으로 세야 한다 (같은 입력이면 같은 결과). 코디 = 상의 1 + 하의 1 + 신발 1
(+ 아우터 0~1)이고, 미분류 옷은 빠진다. 색 조합·계절 충돌·스타일 충돌 규칙은 코드 수정 없이 조정할 수 있어야 한다.
옷에는 별도 '스타일' 속성이 없고 FR-07 속성(fit·material·pattern·season)만 있다.

## 결정
규칙은 `backend/src/main/resources/rules/combo-rules.json` 하나에 두고, 기동 시 읽어 `ComboEngine`을 만든다
(`wearon.combo.rules-location`으로 `file:` 경로의 다른 파일을 지정할 수 있다). 형식이 틀리면 기동이 실패한다.

```json
{
  "version": 1,
  "neutralColors": ["화이트", "블랙", "네이비", "그레이", "베이지"],
  "colorConflicts": [["레드", "그린"], ["오렌지", "퍼플"]],
  "seasonConflicts": [["SUMMER", "WINTER"]],
  "styleConflicts": {"attribute": "pattern", "pairs": [["체크", "스트라이프"], ["체크", "플로럴"], ["스트라이프", "플로럴"], ["도트", "플로럴"]]}
}
```

- 코디가 유효하다 = 코디 안의 **모든 두 벌 쌍**이 충돌하지 않는다.
- 쌍은 순서가 없고, 값은 앞뒤 공백을 지우고 대소문자를 무시해 비교한다. 값이 null이면 충돌로 보지 않는다.
- `neutralColors`의 색은 어떤 색과도 어울린다 (충돌 쌍에 있어도 무시). 같은 색끼리는 충돌 쌍에 없는 한 어울린다.
- `styleConflicts.attribute`는 `pattern`·`fit`·`material` 중 하나다. 스타일 속성이 따로 없어 기본은 패턴 충돌로 본다.
- 셀 대상은 TOP·BOTTOM·SHOES·OUTER뿐이다 (UNCLASSIFIED·ETC 제외).
- 결과는 사용자별로 메모리(Caffeine)에 캐시하되, 계산에 쓴 옷장 스냅샷(옷마다 id·카테고리·색·계절·패턴·핏·소재)을 함께 저장해
  다음 조회 때 스냅샷이 다르면 다시 계산한다. 그래서 등록·수정·삭제·재분류·백필 등 어떤 경로로 옷장이 바뀌어도 낡은 값이 나오지 않는다.

## 검토한 대안
| 대안 | 장점 | 단점 | 버린 이유 |
| --- | --- | --- | --- |
| 규칙을 Java 상수로 | 단순, 타입 안전 | 조정에 코드 수정·배포 필요 | 요구사항(코드 수정 없이 조정) 위반 |
| 어울리는 쌍(허용 목록)을 나열 | 보수적 판정 | 색 수의 제곱만큼 나열해야 하고, 목록에 없는 색은 모두 탈락 | 유지 비용이 크고 대부분의 옷장이 0이 됨 |
| DB 테이블에 규칙 저장 | 운영 중 수정 | 마이그레이션·관리 화면 필요, 결정성 추적 어려움 | 지금 규모에 과함 |
| Redis 캐시 + 변경 시 무효화 | 여러 인스턴스 공유 | 변경 경로마다 무효화를 빠뜨리면 낡은 값 | 스냅샷 비교 방식이 더 안전하고, 계산이 가벼워 인스턴스별 캐시로 충분 |

## 결과
- 규칙 파일만 바꿔 충돌 조합을 조정할 수 있고, 같은 옷장·같은 규칙이면 항상 같은 수가 나온다.
- 기본 충돌 조합(레드–그린 등)은 예시 수준이다. 실제 사용 데이터가 쌓이면 다시 본다.
- 조회마다 옷장 목록은 DB에서 읽는다 (목록 API는 어차피 읽는다). 옷장이 수백 벌 이상으로 커져 전수 열거가 느려지면
  쌍 호환 행렬 기반 계산으로 바꾼다.
- 가상의 새 옷 +N(`ComboEngine.addition`)은 FR-11 살까 말까에서 쓴다.
