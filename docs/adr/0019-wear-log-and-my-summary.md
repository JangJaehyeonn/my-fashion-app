# 0019. 홈 착용 기록·마이 요약: 숫자는 서버가 계산하고, 판정 때 예상 1회 가격을 저장한다

- 상태: 채택
- 날짜: 2026-11-23
- 관련: FR-20, #57

## 배경
FR-20은 홈의 "오늘 이거 입었어요"(FR-10 착용 기록), 이번 주 착용 카드("가장 많이 입은 옷: {이름} · N회"),
마이 탭의 이번 달 요약 3칸(착용 기록 / 살까 말까 / 늘어난 코디)과 "살까 말까로 산 옷"의 "예상 1회 N원 → 지금 1회 N원",
하루 한 번 APP_OPENED(FR-14)를 요구한다.
기존 API에는 다음 값이 없었다.
- `GET /api/wears/summary`의 `mostWorn`에 착용 횟수가 없다.
- `purchase_checks`에 판정 당시의 예상 1회 가격(costPerWear)이 저장되지 않아, 나중에 "구매 전 예상"을 다시 알 수 없다.
- 이번 달 살까 말까 수와 늘어난 코디 수를 주는 API가 없다(`GET /api/purchase-checks`는 최근 20건뿐이라 앱이 셀 수 없다).

CLAUDE.md는 1회당 가격 같은 숫자를 백엔드 결정적 코드가 계산하도록 정한다.

## 결정
- 백엔드에 필드·API를 "추가"만 한다 (기존 필드·동작은 그대로).
  - `mostWorn.count`: 가장 많이 입은 옷의 전체 착용 일수.
  - `purchase_checks.expected_cost_per_wear`(nullable BIGINT): 판정·재판정 때 응답의 costPerWear를 그대로 저장한다. 이전 기록은 다시 계산할 수 없어 백필하지 않는다(NULL).
    멱등 SQL은 `db/phase17_purchase_expected_cost.sql`.
  - `GET /api/purchase-checks` 항목에 `expectedCostPerWear`, `wearCount`(산 옷이 남아 있을 때만), `currentCostPerWear`(가격 ÷ 착용 횟수, 반올림, 가격이 없거나 0회면 null).
  - `GET /api/purchase-checks/summary` → `{monthCount, monthPlus}`: 한국 날짜 기준 이번 달 1일 0시부터의 판정 수와, 그중 산(BOUGHT) 건의 +N 합.
- 앱은 서버 값을 문구로만 바꾼다. 착용 버튼과 주간 카드는 `HomeWearViewModel`, 마이 요약은 `MySummaryViewModel`로 분리해
  위치·인증 같은 안드로이드 의존 없이 JVM 단위 테스트로 검증한다.
- 같은 날 다시 누를 수 없음: 앱이 오늘 기록한 코디(옷 id 집합)를 기억하고, 서버가 모든 옷의 lastWornAt을 오늘로 주면 처음부터 완료로 보인다. 서버도 같은 날 같은 옷을 한 번만 센다(FR-10).
- APP_OPENED: 메인 탭이 보일 때마다 `AppOpenReporter`가 기기 날짜(주입한 Clock)를 SharedPreferences의 마지막 전송일과 비교해 다르면 보낸다. 서버가 받았을 때만 날짜를 저장해 실패하면 다음에 다시 보낸다.

## 검토한 대안
| 대안 | 장점 | 단점 | 버린 이유 |
| --- | --- | --- | --- |
| 앱이 최근 20건으로 이번 달 수·+N 합을 셈 | 백엔드 변경 없음 | 한 달 20건 초과 시 틀림, 숫자를 앱이 계산 | 서버 값과 달라질 수 있다 |
| 지금 1회 가격을 앱이 가격 ÷ 옷장 wearCount로 계산 | API 추가가 적음 | 1회당 가격을 앱이 계산(설계 원칙 위반) | CLAUDE.md 설계 원칙 |
| 예상 1회 가격을 조회 때 다시 계산 | 컬럼 추가 없음 | 지금 옷장·착용 기록으로 계산되어 "구매 전" 값이 아니다 | 요구사항 의미와 다르다 |
| 가장 많이 입은 옷의 횟수를 옷 목록에서 찾음 | 백엔드 변경 없음 | 홈에서 옷 목록을 한 번 더 받아야 함 | 요약 응답에 한 필드를 더하는 편이 단순 |

## 결과
화면의 모든 숫자가 서버 값과 같다. FR-20 이전에 한 판정은 예상 1회 가격이 없어 "지금 1회 N원 · 착용 N회"로만 보인다.
APP_OPENED 날짜는 기기에 계정 구분 없이 저장되므로, 같은 날 한 기기에서 다른 계정으로 바꾸면 그 계정의 APP_OPENED는 다음 날 보낸다.
7일 재방문율에 영향이 보이면 계정별 저장으로 바꾼다.
