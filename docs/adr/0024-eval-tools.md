# 0024. 유사 검색·코디 규칙 평가 도구의 형식과 실행 방식

- 상태: 채택
- 날짜: 2026-11-24
- 관련: FR-24, #71

## 배경
유사 옷 검색(FR-11)의 기준값과 코디 규칙(FR-09)이 사람 판단과 맞는지 재는 도구가 필요하다.
사람이 쓰는 정답 파일(사진 없이)로 돌리고, 실제 임베딩 호출은 `--live`일 때만, CI는 저장된 캐시로 작은 샘플만 돌려야 한다.
FR-09 엔진은 백엔드 Java 코드이고, 인수 테스트는 Python 소켓 차단으로 네트워크를 막은 채 300초 안에 끝나야 한다.

## 결정
- `evals/similarity/run.py`, `evals/combos/run.py` 두 개의 Python 표준 라이브러리 스크립트로 만든다 (새 의존성 없음).
  입력은 JSON(옷 속성 목록·정답 쌍·벡터 캐시·조합 파일), 출력은 마크다운 리포트 한 파일이다. 실행 시각은 넣지 않는다.
- 벡터 캐시는 임베딩 문장(백엔드 `ClothesEmbedder`와 같은 '카테고리 색상 핏 소재 패턴 이름')을 키로 둔다.
  속성이 바뀌면 키가 달라져 낡은 벡터를 쓰지 않고, 캐시에 없으면 실패한다 (몰래 호출하지 않는다).
- `--live`는 AI 서버 `/ai/embed`를 부른다. OpenAI 키는 AI 서버에만 둔다는 규칙을 지키기 위해서다.
- 저장소의 샘플 캐시는 단어 해시로 만든 합성 벡터다 (`make_sample_cache.py`). 실제 OpenAI 호출 없이 만들 수 있어야 해서다.
- 유사도는 소수 6자리로 반올림한 뒤 '기준값 이상이면 비슷함'으로 본다 (FR-11과 같은 경계).
  precision@3은 '비슷함' 쌍이 하나 이상인 옷마다, 정답 쌍이 있는 같은 카테고리 옷을 유사도 순으로 세운 상위 3개 중 '비슷함' 비율의 평균이다.
- combos는 백엔드 규칙 파일을 그대로 읽고 `ComboRules`와 같은 의미로 Python에서 적용한다.
  `evals/combos/parity_cases.json`을 Java(`ComboRulesEvalParityTest`)와 Python 단위 테스트가 함께 확인해 어긋남을 막는다.

## 검토한 대안
| 대안 | 장점 | 단점 | 버린 이유 |
| --- | --- | --- | --- |
| combos가 gradle로 Java 엔진을 직접 실행 | 구현 하나 | 수십 초~분 단위 기동, gradle이 네트워크를 쓸 수 있고 Python 소켓 차단으로 확인 불가 | CI 시간·오프라인 확인 조건에 안 맞음 |
| 백엔드에 평가 API 추가 | 실제 엔진 사용 | 스택이 필요하고 요구사항에 없는 API | 범위 밖 |
| 샘플 캐시에 실제 OpenAI 벡터 저장 | 샘플 수치가 의미 있음 | 만들 때 실제 호출 필요, 1536차원이라 파일이 큼 | 자동 파이프라인에서 실제 호출 금지 |
| `--live`가 OpenAI를 직접 호출 | AI 서버 없이 실행 | 키가 AI 서버 밖으로 나감 | 키는 AI 서버에만 둔다 |

## 결과
- 사람이 정답 파일만 써서 기준값과 규칙 파일 후보를 숫자로 비교할 수 있다. CI는 몇 초 안에 끝난다.
- 샘플 리포트의 숫자는 합성 벡터 기준이라 품질 지표가 아니다. 실제 판단에는 `--live`로 만든 별도 캐시를 쓴다.
- 규칙 의미를 바꾸면(ADR 0008 개정) Python 구현과 `parity_cases.json`도 같이 고쳐야 한다. 어긋나면 두 테스트 중 하나가 실패한다.
